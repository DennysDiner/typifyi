# Tasmanian RTI tracker

Monitoring and tracking system for Tasmania's Right to Information regime: every body with RTI
obligations, their disclosure logs polled aggressively and politely, every fetched document archived
immutably with URL + retrieval time + sha256, silent removals and edits detected, Ombudsman decisions and
annual statistics ingested, plus a private tracker for Kurt's own applications with a statute-driven
deadline engine.

**Read `DECISIONS.md` D3 first**: the build environment could not reach any Tasmanian government site, so
the legal model, registry URLs and adapter formats are evidence-labelled but unverified. The first thing
to do on a machine with network access is the verification pass described below.

## Layout

```
LEGAL_MODEL.md          every statutory rule with its section pinpoint and evidence label
legal/rules.yaml        the machine-readable version the deadline engine reads (no numbers live in code)
legal/holidays/         regional holiday file (unverified until imported from an official source)
registry/authorities.yaml   merged registry (generated by scripts/merge_registry.py)
registry/slices/        research record per slice (state bodies, GBEs/SOCs, local gov + other)
registry/overrides.yaml manual corrections applied on merge
coverage_report.md/.csv authorities with no discoverable disclosure log — a finding in itself
config/                 scheduler tiers, campaign watchlist, alert routing
rti_tracker/            package: db, archive, fetch, adapters/, monitor, scheduler, extract, metadata,
                        deadlines, holidays_cal, applications, watchlist, alerts, health, web/, cli
research/               agent constraints, annual-report cross-check notes, query lists to re-run
tests/                  pytest suite; fixtures/synthetic (hand-built) and fixtures/recorded (live, empty)
deploy/                 cron, systemd timers, GitHub Actions example
```

## Setup

```bash
cd tas-rti-tracker
uv venv --python 3.12 .venv && source .venv/bin/activate
uv pip install -e ".[dev,web]"          # add ,ocr for ocrmypdf (also needs tesseract + ghostscript)
cp .env.example .env && $EDITOR .env    # RTI_CONTACT_EMAIL at minimum
set -a; . ./.env; set +a
rti init                                # migrate DB, sync registry + watchlist + holidays
rti health                              # per-authority freshness (all never_polled at this point)
rti poll --tier 1 --force               # first poll of Tier 1 logs
rti extract && rti metadata             # text + OCR, then LLM metadata (needs ANTHROPIC_API_KEY)
rti alerts --dry-run                    # see what would be sent
rti web                                 # http://127.0.0.1:8765 (basic auth if RTI_WEB_USER set)
datasette data/rti.db -m rti_tracker/web/datasette_metadata.yaml   # faceted exploration
pytest -q
```

Scheduled operation: `rti run` is one tick (poll what is due, extract, link applications, send immediate
alerts). Run it every 10 minutes from cron or the systemd timer in `deploy/`; the tick decides what is due
(Tier 1 hourly, Tier 2 six-hourly, configurable in `config/scheduler.yaml`). `rti alerts --digest` sends
the daily digest. `rti archive verify` re-hashes every blob.

## First run on a networked machine (verification pass)

1. Allow the hosts listed in `DECISIONS.md` D3 in the environment's network policy.
2. Re-read the Act: work through the checklist at the end of `LEGAL_MODEL.md`, fix `legal/rules.yaml`,
   flip `evidence` to `primary_source` and clear `uncertain` flags. `pytest tests/test_deadlines.py` reads
   the numbers from the rules file, so the worked examples follow.
3. `rti holidays import-csv` from WorkSafe Tasmania's statutory holidays page.
4. Download the RTI annual reports (Department of Justice) and run `rti annual import <pdf> --year 2024-25`
   then `rti annual crosscheck`. Every unresolved name is a registry gap: add it to
   `registry/overrides.yaml` (or the right slice) and re-run `rti registry merge && rti registry sync`.
5. `rti poll --force` for everything; `rti registry suggest-formats` to see what the `auto` adapter detected;
   write the detected formats back into the registry; `rti fixtures record <id>` for each authority so the
   adapter tests replay real pages.
6. Re-run the research queries listed under `queries_not_run` / `failed_queries` in the slice files and in
   `research/annual_report_crosscheck.md` to fill the disclosure-log gaps.

## How to add an authority

Add a record to `registry/overrides.yaml` (new bodies) or the right slice file (research corrections),
following the schema in `registry/slices/*.yaml` (id slug, name, type, rti_status with basis, portfolio
minister, URLs with evidence labels, `disclosure_log_format`, optional `adapter`, `adapter_config`, `tier`,
`region`, `extra_sources`). Then:

```bash
rti registry merge && rti registry validate && rti registry sync && rti poll --authority <id>
```

Bodies that are business units of a department (offices, divisions, services) are typed `business_unit`
with `rti_status: via_parent`; they are excluded from coverage counts and health.

Renames and machinery-of-government changes: add the old name to `name_history` (or `aliases`) and an entry
to `mog_changes` with the effective date; never delete the old record — set `active: false` and name the
successor in `notes`. `authority_names` / `authority_urls` in the DB are append-only so historical releases
stay attributable.

## How to add an adapter

Generic adapters (`html_table`, `html_list`, `pdf_index`, `per_release_pages`, `auto`) cover most logs via
`adapter_config` (CSS selectors, column maps, `next_selector` for pagination, `extra_listing_urls`). For a
site that defies them:

1. Create `rti_tracker/adapters/bespoke/<site>.py`, subclass `Adapter`, decorate with `@register("<name>")`,
   implement `parse(body, base_url, config) -> list[ListedItem]` (pure, no network) and optionally
   `next_page` / `expand`. `ListedItem.external_key` must be stable across polls (reference number, or
   `stable_key(title, url)`).
2. Set `adapter: <name>` on the authority record and sync.
3. Record a fixture: `rti fixtures record <authority_id>` writes `tests/fixtures/recorded/<id>/` and the
   replay test picks it up automatically. Merge only when it passes.

## Applications tracker

```bash
rti app new --authority stt --lodged 2026-08-03 --accepted 2026-08-03 --scope "coupe plans …" --reference RTI-26-77
rti app event 1 third_party_consultation_decided 2026-08-12
rti app event 1 decision_notified 2026-09-25 --detail '{"decision_maker":"delegate","outcome":"partial"}'
rti app attach 1 ./decision-letter.pdf
rti app status 1                     # statutory dates, state (with section), what you can do next
rti app events                       # the event vocabulary
```

Every date shows its rule id, section, evidence label and UNCERTAIN flags, and a second date where the
regional-holiday reading differs. Alerts fire 5, 2 and 0 working days before each deadline and on any
deemed refusal. Releases matching an application by reference number or scope words are proposed as links.

## Alerts

`config/alerts.yaml` routes: immediate for Tier 1 new releases, watchlist matches, removals/edits/changed
documents, adapters failing > 24 h, blocked sources, and application deadlines; everything else goes into
the daily digest. Channels activate from env vars (`RTI_NTFY_URL`, or the SMTP set). Campaign keywords are
in `config/watchlist.yaml`; `rti campaign sync` reloads them; `rti campaign pack <id>` exports a citation
pack (source URL, retrieval time, sha256, archived copy path).

## Adapter limits (what the tool cannot see yet)

Logs published as spreadsheets or Word files, JavaScript-rendered lists (SharePoint, Power BI, "load more"
buttons, AJAX pagers) and PDF indexes with wrapped rows are not parsed by the generic adapters; a site behind
a bot challenge shows as `blocked`. Each of these is a coverage gap to report, not a reason to work around
the site. `rti health` exits non-zero while any Tier 1 body has no source.

## Provenance

Every fetch is a `captures` row (URL, final URL, time, status, headers, sha256) chained to the previous one;
the tables are append-only at the database level and blobs are read-only files. `rti archive verify`
re-hashes blobs, verifies the chain and prints its head — anchor that head externally (OpenTimestamps or a
dated public post) so the ledger is tamper-evident against the machine's owner too. Removal records carry
the last capture that contained the entry and the first that did not.

## Hosting and access

Private by default: the web UI binds to 127.0.0.1 and can require basic auth; Datasette hides the
application tables. Do not expose either publicly without deciding what to do about third-party personal
information inside released documents and copyright in re-published material (brief §4).
